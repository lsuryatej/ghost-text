# Ghost Text — inference bench

Generated by `ghost-bench` (`Sources/ghost-bench/`) against `GhostTextInference.CompletionEngine`
on an Apple M5, 16 GB, macOS 27, mlx-swift 0.31.6. Machine-generated sections are marked with
`<!-- ... -->` comments and are safe to regenerate by rerunning the tool; everything else on this
page is written by hand after reading the numbers below.

**`swift build` alone produces a binary that cannot run inference.** See
[MLX build friction](#mlx-build-friction) — you must build via `xcodebuild`, once, with the Metal
toolchain installed:

```
xcodebuild -downloadComponent MetalToolchain     # once per machine

xcodebuild build -scheme ghost-bench -destination 'platform=macOS' \
    -derivedDataPath .build/xcode -skipPackagePluginValidation -skipMacroValidation

.build/xcode/Build/Products/Debug/ghost-bench                 # latency mode, both models
.build/xcode/Build/Products/Debug/ghost-bench --quality       # quality mode, both models
```

## The question this phase exists to answer

The original design assumed a persistent KV cache across keystrokes is mandatory, to avoid
re-prefilling the whole buffer on every pause. That's only true if a full re-prompt is too slow.
**Verdict:** see [KV-cache verdict](#kv-cache-verdict) below.

## KV-cache verdict

**Yes — a full re-prompt is well under 150ms end-to-end at a 200-character buffer. Skip
persistent KV-cache/prefix-reuse logic for v1.**

At 200 characters (roughly a full sentence of typed context), `complete()` end-to-end:

| Model | p50 | p95 | max |
|---|---|---|---|
| Qwen2.5-0.5B-Instruct-4bit | 115ms | 117ms | 121ms |
| Qwen2.5-0.5B-4bit (base) | 125ms | 126ms | 126ms |

Both are roughly **25-35ms under the 150ms budget at p95**, with very little variance (max stays
within a few ms of p95 — no long tail). The trend across buffer lengths is flat, not linear:
20 chars costs about the same as 400 chars (108-129ms across the board), because prefill
(`promptTime` in the tables above) is a small, roughly-constant 18-23ms slice of the total — the
tokenizer and a 0.5B 4-bit forward pass over a few dozen to ~100 prompt tokens is cheap on an M5.
The dominant cost is decode: ~90-110ms to sample `maxTokens=12` tokens one at a time, which is
*inherent to next-token generation* and unaffected by whether the prompt was cached or freshly
prefilled. A KV cache would only ever save the 18-23ms prefill slice, and only for buffers long
enough that re-tokenizing+re-embedding them is non-trivial — at the buffer lengths this app
actually sees (a line or two of in-progress typing, not a document), that slice barely moves.

Concretely: the entire premise for cache-trimming logic — "prefill dominates and grows with
buffer length" — didn't hold. Prefill is flat and small; decode dominates and is fixed by
`maxTokens`. Implementing KV-cache reuse across keystrokes would add an entire subsystem (cache
lifetime, invalidation on backspace/non-append edits, `RotatingKVCache`/quantized-cache tuning —
see [KV cache reuse, if it *were* needed](#kv-cache-reuse-if-it-were-needed) below for what that
would actually involve) to shave single-digit milliseconds off a call that's already 25ms+ under
budget. Not worth it for v1. Revisit only if `maxTokens` grows substantially (e.g. multi-sentence
completions) or buffers routinely exceed a few hundred characters.

### KV cache reuse, if it *were* needed

For the record — `mlx-swift-lm` (the successor to `mlx-swift-examples`; see
[the mlx-swift-lm split](#the-mlx-swift-lm-split) below) does expose real prefix-reuse primitives
today, they're just unneeded here:

- `TokenIterator` and `generate(...)`/`generateTask(...)` all accept an optional
  `cache: [KVCache]?`. Passing the *same* `[KVCache]` array back into a second call continues
  generation from wherever that cache's `offset` left off — i.e. the mechanism for "don't
  re-prefill what you already prefilled" already exists at the API level.
- `KVCacheSimple` (default, unbounded), `RotatingKVCache` (fixed-size sliding window via
  `maxKVSize`), and `QuantizedKVCache` (4/8-bit) are the concrete cache types
  (`Libraries/MLXLMCommon/KVCache.swift` in the resolved checkout).
- `canTrimPromptCache(cache)` / `trimPromptCache(cache:numTokens:)` support trimming the *end* of
  a cache — exactly what backspace/edit-that-invalidates-the-tail would need.
- What it does **not** give you for free: cache *invalidation* logic (deciding whether a new
  keystroke buffer is "the old buffer plus an append" vs. "an edit in the middle" that requires a
  partial or full re-prefill), or wiring that decision into `CompletionEngine`. That's the actual
  complexity the original design was worried about, and it's still all bespoke work on top of
  these primitives — not something `mlx-swift-lm` hands you.

## MLX build friction

Things that will bite whoever wires `GhostTextInference` into `GhostTextApp` next, none of which
were true of the API surface the original task brief assumed:

### The mlx-swift-lm split

`MLXLLM` and `MLXLMCommon` no longer live in `mlx-swift-examples` — as of that repo's commit
`0db7c5d` ("split out mlx-swift-lm"), they were extracted into a **new repo**,
[`ml-explore/mlx-swift-lm`](https://github.com/ml-explore/mlx-swift-lm). `mlx-swift-examples`
`main` today only vends `MLXMNIST` and `StableDiffusion`; pointing `Package.swift` at it for
`MLXLLM`/`MLXLMCommon` fails to resolve those products at all. `Package.swift` here depends on
`mlx-swift-lm` directly.

### mlx-swift-lm 3.x decoupled its downloader/tokenizer

The old `LLMModelFactory.shared.loadContainer(configuration:)` (no downloader argument) is gone.
`mlx-swift-lm` 3.x's `ModelFactory` is downloader/tokenizer-agnostic — you supply conformances to
its `Downloader` and `TokenizerLoader` protocols. The path of least resistance (and the one used
here) is the maintainers' own `MLXHuggingFace` product, which provides
`#hubDownloader()` / `#huggingFaceTokenizerLoader()` macros wrapping `swift-huggingface`'s
`HubClient` and `swift-transformers`' `AutoTokenizer`. That pulled two more package dependencies
into `Package.swift` beyond `mlx-swift-lm` itself: `huggingface/swift-huggingface` (product
`HuggingFace`) and `huggingface/swift-transformers` (product `Tokenizers`) — the macro-expanded
code references those types directly, so the *call site* needs them, not just `MLXHuggingFace`.
Default HF cache dir (`~/.cache/huggingface/hub`, Python-compatible) works with no extra config.

### `swift build` / `swift run` cannot produce a working MLX binary

This is the big one. mlx-swift's own README says outright: *"SwiftPM (command line) cannot build
the Metal shaders so the ultimate build has to be done via Xcode."* This version (0.31.6) has no
build-tool plugin that compiles `.metal` → `.metallib` when invoked via plain `swift build`; the
resulting binary compiles and links fine, but crashes on first use with:

```
MLX error: Failed to load the default metallib. library not found ...
```

`DESIGN.md`'s hard constraint #6 ("MLX ships Metal shaders in a SwiftPM resource bundle... copy
every `.bundle` into `Contents/Resources/`") undersells this: it's not that a hand-assembled
`.app` misses a bundle that `swift build` already produced — **`swift build` never produces a
working `default.metallib` in the first place** with this dependency version. `scripts/build.sh`
runs plain `swift build -c release --product GhostTextApp`, so as written it will assemble an
`.app` that launches, loads the model metadata, and then throws at the first `warmup()`/`complete()`
call. The fix is to build via `xcodebuild` instead (which *can* invoke the Metal compiler):

```
xcodebuild -downloadComponent MetalToolchain   # one-time, ~690MB, needed for `xcrun metal`
xcodebuild build -scheme GhostTextApp -destination 'platform=macOS' \
    -derivedDataPath .build/xcode -skipPackagePluginValidation -skipMacroValidation
```

This produces `mlx-swift_Cmlx.bundle/Contents/Resources/default.metallib` under
`.build/xcode/Build/Products/<config>/`, alongside the other resource bundles (`swift-transformers_Hub.bundle`,
`swift-crypto_Crypto.bundle`) that `scripts/build.sh`'s existing `*.bundle` copy loop will pick up
correctly once it's pointed at the xcodebuild output directory instead of `.build/<config>`.
`-skipPackagePluginValidation` and `-skipMacroValidation` are needed because `xcodebuild` (unlike
`swift build`) prompts for one-time trust of the `CudaBuild` build plugin and the
`MLXHuggingFaceMacros` compiler plugin; both are non-interactive-safe to pre-approve for CI.

Everything in this repo's own scope (`GhostTextInference`, `ghost-bench`) still satisfies "`swift
build` passes" as a *compiles* check — that's true and stayed true throughout. It just isn't
sufficient to produce a runnable binary, which is a materially different (and worse) guarantee
than `DESIGN.md` assumed.

### Prompt framing has to bypass the built-in chat template

`MLXLMCommon.Tokenizer.applyChatTemplate` (and the default `LLMUserInputProcessor` that
`UserInput`/`processor.prepare(input:)` goes through) always terminates with a closed,
generation-ready assistant turn — there's no `addGenerationPrompt: false` or "continue the final
message" knob exposed through that protocol (swift-transformers' own `Tokenizer.applyChatTemplate`
has an `addGenerationPrompt` parameter, but the 3-argument overload `MLXLMCommon.Tokenizer`
actually calls always passes `true`). So `CompletionEngine` bypasses `UserInput`/chat-template
entirely and builds the token sequence itself via `Tokenizer.encode(text:addSpecialTokens:)` —
for instruct models, that means hand-writing an unterminated ChatML-style prompt (see
`PromptFraming.chatPrefill` in `Sources/GhostTextInference/GhostTextInference.swift`) rather than
using the library's chat-template path at all. See [Quality](#quality) below for how much this
mattered in practice.

### Cancellation needs the task handle, not just `Task.isCancelled`

`generate(input:...)` internally calls `generateTask(...)` and discards the `Task` handle — so if
you use the plain `generate()` free function, there is no way to stop the underlying generation
early; the `AsyncStream` just keeps being fed until the model finishes on its own. `Task.isCancelled`
checked inside the `for await` loop only reflects *your own* calling task, not the detached-ish
`Task` that `generateTask` spawns internally to drive the token loop — cancelling your task does
**not** propagate into it automatically. `CompletionEngine.complete` therefore calls
`generateTask(...)` directly (not `generate(...)`) to keep the `Task` handle, checks
`Task.isCancelled` on every streamed `Generation` event, and explicitly calls `task.cancel()` +
`await task.value` before returning when it fires. This is documented as the intended pattern
(`mlx-swift-lm`'s own skill reference calls it the "Task-Handle Pattern for Early Stop") but it's
easy to miss if you reach for the simpler `generate()` entry point first.

Verified with a throwaway smoke test (not shipped — the pattern is exercised implicitly by
`complete`/`completeWithTiming`'s own logic): call `complete(buffer:maxTokens: 300)` in a `Task`,
cancel that task ~30ms in, `await task.value`. It returned **4ms after `cancel()`**, with a
13-character partial result — not the ~2.5s a 300-token generation would otherwise take. Confirms
cancellation actually stops generation rather than running to completion in the background.

### Framing A/B on the instruct model

The table above uses each model's *inferred* framing (`PromptFraming.inferred(fromModelID:)`):
`chatPrefill` for the Instruct model, `raw` for the base model. To verify that heuristic rather
than assume it, the Instruct model was also run with `--framing raw` (`ghost-bench --model
mlx-community/Qwen2.5-0.5B-Instruct-4bit --quality --framing raw`), i.e. feeding it the buffer
with no chat wrapping at all, the same way the base model is fed:

| Buffer | `chatPrefill` (assistant-turn prefill trick) | `raw` (no framing) |
|---|---|---|
| `She opened the door and` | ` stepped inside, her heart racing with excitement. The warm sun` | ` asked the door to ______．（ ） A. open` |
| `He walked into the room and immediately` | ` felt the warmth of the sun on his skin.` | ` saw the door was open. He ________ to the door` |
| `Once the meeting wraps up,` | ` the project team will review the progress and identify areas for improvement` | ` the organizers should _____. A. Summarize the meeting` |
| `The stock market fell sharply after the announcement.` | *(empty — model closed the turn immediately)* | ` The stock market fell by 10% in the first` |
| `Let me know what you think. ` | *(empty)* | `1. What is the meaning of the word "universe` |

`raw` on the Instruct model reliably drifts into exam/quiz artifacts — fill-in-the-blank
underscores, `A. B. C.` multiple-choice options, occasionally non-English text (`____（进入）`
showed up in one run) — a well-known side effect of instruct fine-tuning corpora that mix in a lot
of QA/exam-style data. `chatPrefill` (open the assistant turn with the buffer already "said" and
let the model continue it, never closing with `<|im_end|>`) avoids that failure mode almost
entirely: the completions read as continuations of the sentence, not as answers to a question.
The one new failure mode `chatPrefill` introduces is the model deciding the sentence was already
complete and closing its own turn (empty completion) — happened twice in twenty prompts, both on
buffers that already read as complete sentences. Net, `chatPrefill` is the better default for
instruct-tuned models here; `PromptFraming.inferred(fromModelID:)` codifies that.

## Model recommendation

**Use `mlx-community/Qwen2.5-0.5B-Instruct-4bit`, with `PromptFraming.chatPrefill` (the inferred
default).**

- **Latency**: both models comfortably clear budget (see [Latency](#latency)), and if anything the
  Instruct model was slightly *faster* end-to-end (108-118ms p50/p95 across buffer lengths vs.
  124-134ms for the base model) — not a large enough gap to be conclusive on its own given the
  sample size, but it rules out "the better-quality model is the slower one."
- **Quality**: this is where they actually diverge. The base model, even with `raw` framing (its
  natural mode — it has no chat template to bypass), repeatedly drifts into the same
  exam-artifact failure mode described above: `A. comfort`, `____（进入）`, `1. 2015 - 201`,
  `______.⏎A. dropped sharply`. That's a symptom of what it was pretrained on, not a framing
  problem — there's no framing fix available for a base model. The Instruct model with
  `chatPrefill` didn't produce a single quiz-artifact completion across its 20-prompt run; its
  failure mode (occasionally closing the turn early on already-complete sentences) is much less
  disruptive for an autocomplete UI — an empty suggestion is a no-op, a `A. B. C.` suggestion is
  actively wrong to insert into someone's sentence.
- Net: the instruct-tuned model, driven with the assistant-prefill trick instead of its normal
  chat template, gives the more reliable continuation behavior *and* isn't the slower option.
  There's no tradeoff to accept here.
